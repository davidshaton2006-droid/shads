# SHADS — приватный агент управления рекламой (Яндекс.Директ / VK Ads)

Личная система Давида: ИИ-агент (Claude) читает и правит кампании в Яндекс.Директе и VK Ads
через собственные OAuth-доступы, без сторонних сервисов вроде LidFly. Авито, лендинги и SEO
в систему не входят — они ведутся отдельно вручную.

## Архитектура

```
skills/                    — плейбуки (обязательное чтение агентом перед решениями)
  yandex-direct-playbook.md
  vk-ads-playbook.md
supabase/migrations/       — схема БД (проекты, лимиты, guardrails, лог действий)
src/
  providers/                — тонкие обёртки над Яндекс.Директ / Метрика / VK Ads API
  oauth/                     — OAuth-флоу для Яндекса и VK
  lib/                       — supabase-клиент, шифрование токенов, чтение connections
  guardrails/                — preflight, стоп-кран, каталог типов действий
  mcp/                       — MCP-сервер и инструменты для агента (read + write)
  routes/, dashboard/        — Express API + минимальный веб-дашборд
```

Почему такой стек: Node/Express (уже используете), Supabase (уже используете) для хранения
проектов/лимитов/токенов/истории, MCP поверх Express-процесса — так агент (Claude) получает
инструменты напрямую, а дашборд и агент работают с одной и той же guardrail-логикой
(`src/guardrails/preflight.js`), а не с двумя параллельными реализациями.

## Guardrails — как это работает

1. **Дневной лимит бюджета** ставите вручную в самой площадке (в настройках кампании) —
   `daily_budget_limit` в Supabase это дублирует для контроля/алертов, но не заменяет.
2. **Preflight**: каждый write-инструмент MCP (`src/mcp/tools/yandex.js`, `vk.js`) идёт через
   `guardedWrite` → `requestAction`. Если тип действия для проекта не помечен автономным,
   создаётся `pending_action` и агент получает отказ с просьбой попросить подтверждение —
   выполнить действие в обход этого пути невозможно, т.к. `providers/*.js` не имеют токенов
   без прохода через `src/lib/connections.js`, а вызываются только из `mcp/tools/*` и
   `routes/api.js` (после ручного approve).
3. **Staged autonomy**: таблица `project_action_settings` + дашборд-переключатель на каждый
   тип действия (`negative_keyword.add`, `bid.update`, `budget.update`, ...). По умолчанию —
   везде `requires_confirmation = true`.
4. **Стоп-кран**: `src/guardrails/stopCranRunner.js` каждые 5 минут (см. `src/server.js`)
   проверяет правила `stop_rules` (`cpa_ceiling`, `spend_no_conversions_pct`) независимо от
   агента и от того, спит он или ошибся — при срабатывании кампании ставятся на паузу и
   пишется `stop_events`.
5. **Лог и откат**: любое реально выполненное действие пишется в `action_log` с
   `previous_state`/`result` — просмотр в дашборде.

⚠️ **Сбор реальных метрик для стоп-крана (`getSpendAndConversionsFor` в
`stopCranRunner.js`) сейчас — заглушка, возвращающая нули.** Это сделано намеренно: пока
функция не подключена к реальным отчётам Директа/VK и не покрыта тестами, стоп-кран не может
сработать по ложным данным, но и не защищает бюджет по-настоящему. **Не давайте агенту право
на автономные write-действия, пока это не реализовано и не проверено на реальных цифрах.**

## Плейбуки — обязательная часть логики агента

`skills/yandex-direct-playbook.md` и `skills/vk-ads-playbook.md` — не просто документация.
MCP-инструмент `get_playbook` (`src/mcp/tools/playbooks.js`) должен вызываться агентом перед
любым предложением по структуре кампании, стратегии ставок или минус-словам — аналог
`get_methodology` у LidFly. Каждый write-инструмент в описании (`description`) ссылается на
конкретный раздел плейбука, которому должно соответствовать действие.

## Установка

```bash
npm install
cp .env.example .env
```

Заполните `.env`:
- **Supabase**: создайте новый проект на supabase.com (отдельный от других ваших данных —
  здесь хранятся OAuth-токены клиентов), примените миграцию:
  ```bash
  npx supabase db push --db-url "postgresql://postgres:<пароль>@<host>:5432/postgres"
  # или вручную: скопируйте содержимое supabase/migrations/0001_init.sql в SQL Editor проекта
  ```
- **TOKEN_ENCRYPTION_KEY**: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`
- **Яндекс OAuth**: зарегистрируйте приложение на https://oauth.yandex.ru/client/new —
  доступы "Яндекс.Директ API" и "Яндекс.Метрика: чтение данных", redirect URI как в `.env`.
- **VK Ads OAuth**: зарегистрируйте приложение в кабинете VK ID (https://id.vk.com/business) с
  доступом к VK Ads API — точный флоу свериться в актуальной справке на момент регистрации
  (VK периодически меняет домены/эндпоинты для API, см. TODO-комментарии в `src/oauth/vk.js`
  и `src/providers/vkAds.js`).

Запуск дашборда:
```bash
npm run dev
# http://localhost:3000
```

Запуск MCP-сервера (для подключения к Claude Desktop/Code — добавьте в конфиг MCP-серверов
команду `node <путь>/src/mcp/server.js` с рабочей директорией проекта и тем же `.env`):
```bash
npm run mcp
```

## План тестового запуска (обязательно перед боевым использованием)

1. Один пилотный проект с минимальным дневным бюджетом (например, 300–500 ₽/день).
2. Все типы действий — в режиме "требует подтверждения" (дефолт, ничего не трогать).
3. Минимум 2 недели ведения через дашборд: агент предлагает действия → вы подтверждаете
   каждое → смотрите на `action_log`, нет ли неожиданных или ошибочных вызовов.
4. Проверить, что стоп-кран (после реализации сбора реальных метрик, см. предупреждение выше)
   срабатывает на синтетическом тесте — например, временно занизить `threshold` в `stop_rules`
   и убедиться, что кампания реально ставится на паузу и `stop_events` пишется.
5. Только после этого рассматривать перевод отдельных low-risk типов действий
   (`negative_keyword.add`, `ad.pause`, `placement.exclude`) в автономный режим — и то по
   одному, с наблюдением за логом минимум неделю на каждый.
6. `budget.update` и `strategy.change` — оставлять на подтверждении постоянно, независимо от
   результатов пилота (это прямое требование из плейбуков, раздел 9 в обоих файлах).

## Лидген — поиск клиентов (src/leadgen/)

Отдельный модуль, не связанный с ведением рекламных кабинетов: ищет потенциальных клиентов
(компании) в открытых источниках — объявления Авито и карточки компаний 2ГИС — по нише и
городу, вытаскивает контакт (Telegram/WhatsApp/email) из текста и готовит персонализированный
черновик предложения о сотрудничестве. Дашборд: вкладка "🎯 Поиск клиентов".

**Осознанное ограничение: отправки нет и не будет автоматической.** Система только находит и
готовит черновик — копирует владелец сам, вручную, из своего Telegram/WhatsApp/почты. Это не
недоработка, а решение после обсуждения рисков: массовая рассылка, замаскированная под живого
человека, — это по механике то же самое, что спам-бот, обходящий антиспам-защиту площадок;
она банит рабочие аккаунты/номера и потенциально нарушает закон "О рекламе" (нужно согласие
получателя) и правила площадок-источников. Не добавляйте `leadgen_send`-инструмент без
пересмотра этого решения.

Ограничения самого поиска (см. комментарии в `src/leadgen/parsers/*.js`):
- Авито прячет телефон за защищённым эндпоинтом — контакт находится, только если продавец сам
  указал Telegram/WhatsApp/почту в описании объявления. Селекторы HTML могут ломаться при
  обновлении вёрстки Авито — если поиск стабильно возвращает 0 объявлений, проверяйте их первыми.
- 2ГИС требует API-ключ (`TWOGIS_API_KEY`, бесплатный на https://dev.2gis.ru) — но чаще отдаёт
  телефон/сайт открыто, это публичные бизнес-данные компании.
- Не увеличивайте `limit`/частоту запусков агрессивно — Авито банит IP по rate-limit/капче.

## Что не входит в эту систему

Лендинги, SEO — ведутся отдельно вручную, агент их не касается. Авито теперь частично покрыт
модулем лидгена (поиск клиентов), но ведение самих объявлений на Авито — по-прежнему вручную.
